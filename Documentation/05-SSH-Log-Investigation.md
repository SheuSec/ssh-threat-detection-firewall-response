# SSH Log Investigation

## Objective

After generating the controlled SSH authentication event from Kali Linux, I moved to the investigation phase.

The objective was to examine the Ubuntu authentication logs and determine what information had been recorded about the SSH activity.

As a cybersecurity analyst, I wanted to answer several basic questions:

- What happened?
- When did it happen?
- Which account was involved?
- Which system generated the request?
- Was the authentication successful or unsuccessful?
- Where was the evidence recorded?

The main log used during this investigation was:

/var/log/auth.log

Implementation

I started by examining the authentication log on the Ubuntu server.

I used:

sudo tail -n 50 /var/log/auth.log

This displayed the most recent authentication events recorded by the system.

Because the log can contain many different types of authentication activity, I narrowed the search to SSH-related events.

I used:

sudo grep "sshd" /var/log/auth.log | tail -20

This allowed me to focus on events generated by the SSH daemon.

I then searched specifically for invalid users:

sudo grep "Invalid user" /var/log/auth.log

The result showed the failed authentication event generated during my controlled test.

The entry contained information identifying the invalid username and the source IP address.

Investigating the Source IP

The source IP was one of the most important pieces of information in the event.

The log identified the source as:

192.168.10.101

I compared this address with the network configuration established earlier in the project.

I had previously identified:

192.168.10.100

as the Ubuntu server and:

192.168.10.101

as the Kali Linux testing machine.

This allowed me to establish that the authentication event came from the Kali system.

This was an important part of the investigation because an IP address in a security log is only useful when it can be placed into the context of the environment.

Investigating Failed Authentication Events

I also searched for failed password authentication events using:

sudo grep "Failed password" /var/log/auth.log

I used tail when I wanted to focus on the most recent events:

sudo grep "Failed password" /var/log/auth.log | tail -10

This provided a quick way to review recent failed SSH authentication activity.

I also searched for invalid users:

sudo grep "Invalid user" /var/log/auth.log | tail -10

Using these searches made it easier to separate potentially relevant authentication events from the rest of the system log.

Evidence Analysis

The investigation allowed me to identify several important fields from the SSH event.

Field	Finding
Service	SSH
SSH Port	22
Source IP	192.168.10.101
Target IP	192.168.10.100
Username	wronguser
Event Type	Invalid SSH user
Result	Authentication unsuccessful

The information matched the controlled activity that I generated from Kali.

This correlation was important because it demonstrated that the event seen in the log was directly related to the test I had performed.

Verification

To make sure that I was not relying on a single log entry, I compared the authentication records with the known activity from the testing machine.

The source address recorded in the log matched the Kali Linux address.

The target system was the Ubuntu server.

The username recorded in the event also matched the invalid username used during the test.

This provided enough evidence to establish a relationship between the generated activity and the log entry.

Outcome

The SSH authentication logs successfully recorded the controlled event generated from Kali Linux.

The investigation identified:

Source:      192.168.10.101
Target:      192.168.10.100
Service:     SSH
Username:    wronguser
Event:       Invalid user

The log investigation therefore provided the evidence needed to move into the detection stage of the project.

Rather than manually reviewing the authentication log every time, I wanted to create a simple mechanism that could identify these events automatically.

Reflection

This stage was one of the most useful parts of the project because it showed me how much information can be obtained from a relatively simple Linux authentication log.

At first, a log entry can look like a collection of technical information. However, once I understood the fields, I could reconstruct what had happened:

Kali generated the connection → Ubuntu received it → SSH processed the authentication attempt → Ubuntu recorded the event.

The investigation also reinforced the importance of knowing the normal environment before investigating suspicious activity.

Because I already knew that 192.168.10.101 belonged to my Kali testing machine, I could correctly interpret the event instead of treating the address as an unknown attacker.

The next logical step was therefore to automate the identification of these events using a Bash detection script.
